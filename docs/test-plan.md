# 测试规划 (Test Plan)

- 项目：Windows 文件共享回收站 (RecycleBin for SMB)
- 范围：内核 Mini-Filter 驱动 (`rbminiflt`) + C 核心服务 (`rbservice`) + Go 管理 API (`rbapi`) + 数据模型 (SQLite) + 部署链路 (`deploy.ps1`)
- 日期：2026-09-01
- 对应缺陷：**RB-15**（测试覆盖为零，P2，待修）
- 目标：建立分层测试网，使缺陷由测试发现，而非由事故发现

> 文档关系
>
> - `buglist.md` — 现存问题清单与整改排期（本文的回归用例来源）
> - `bugfix-production.md` — 已修复缺陷的根因与方案（本文的回归验证依据）
> - `design.md` — 架构与核心范式（本文的测试对象定义）
> - `test-plan.md` — 本文件，测试策略、用例清单与准出标准

## 零、现状与动机

### 现有测试资产

| 资产 | 覆盖 | 局限 |
|---|---|---|
| `db/verify_contract.py`（9 项） | C ↔ Go 共享 schema：版本校验、列存在性、`CHECK` 约束、Go 读 C 建库、`display_path` 偏好 | 只验证**结构契约**，不覆盖任何行为 |
| `db/verify_c_contract.py`（10 项） | C 版本守卫、ops 入队→执行→回写往返 | 单次往返，无并发/失败路径 |
| `db/verify_stats_endpoint.ps1` | `/stats`、`/health` 端点字段 | 无断言基线，需人工判读 |
| `deploy.ps1` [7/6] 冒烟 | 部署后拦截链路是否 LIVE（RB-29 新增） | 仅部署时执行，非回归套件 |

**Go 层无单元测试文件，C 层无测试 harness，驱动层无 HLK / Verifier 测试。**

### 关键教训：缺陷几乎全部由"事故 + 人工取证"发现

回顾已修复的 30 条缺陷，其发现途径值得警惕：

| 发现途径 | 对应缺陷 | 说明 |
|---|---|---|
| 代码审查 | RB-01 ~ RB-12 | 静态可见，属评估阶段产出 |
| **实测蓝屏 + dump 反汇编** | RB-27、RB-28 | 上线后连续两次 BSOD 才定位 |
| **实测取证（USN Journal）** | RB-29 | 用户文件被永久删除后才追溯出 attach 窗口 |
| **用户反馈"看不到"** | RB-30 | 还原功能 100% 受影响，靠用户报障发现 |
| 契约测试捕获 | 1 次（`once` 模式 ops 未排空回归） | 唯一一次由测试捕获的回归 |

**结论**：现有"测试"只挡住了结构漂移，行为缺陷（尤其是内核路径与端到端语义）完全无网。本规划的核心目标是**把已修缺陷逐条固化为回归用例**，并补齐行为层测试。

### 两条必须贯彻的原则

1. **以构建产物为准**：RB-27 / RB-28 的教训是"源码看似已修、产物实际未编译进去"。内核相关验证必须核对部署到 `System32\drivers\` 的 `.sys` 的 SHA256 与构建产物一致，必要时反汇编 / IAT 核对。
2. **数据安全优先**：任何测试**不得**在承载真实数据的卷或生产共享上执行；所有用例须验证 fail-closed 生效（拒绝删除保住数据），禁止出现静默真删。

## 一、测试分层

| 层级 | 测试对象 | 手段 | 自动化 | 环境要求 |
|---|---|---|---|---|
| **L0** | 编译期与静态契约 | `C_ASSERT` / 结构体偏移断言 / 编译零警告 | 全自动（构建即跑） | 构建机 |
| **L1** | 单元逻辑 | Go `go test`；C 侧轻量 harness | 全自动 | 构建机 |
| **L2** | 跨层契约 | `db/verify_*.py` + `verify_stats_endpoint.ps1` | 全自动 | 构建机（临时 DB） |
| **L3** | 用户态集成 | C 服务 + Go API + SQLite 闭环（Pester 编排） | 全自动 | 测试机（无需驱动） |
| **L4** | 驱动 / 内核 | Driver Verifier + HLK 基础项 + 专项驱动用例 | 半自动（需人工触发） | **独立测试机**（会蓝屏） |
| **L5** | 端到端（SMB） | 真实删除→拦截→还原，本地 / UNC / 映射盘 | 半自动 | 测试机 + 客户端 |
| **L6** | 非功能 | 压测、故障注入、长稳、安全 | 半自动 | 测试机 |

> 分层原则：**能在用户态验证的，绝不进内核**。内核用例成本高（重启、蓝屏、dump 分析），只有真正依赖 I/O 路径的语义才上 L4/L5。

### L4 驱动 / 内核（独立测试机，Driver Verifier 必开）

> **前置**：Verifier 对 `rbminiflt.sys` 启用 Special Pool、Pool Tracking、I/O Verification、Deadlock Detection、DMA Checking（其余按 HLK 建议）；内核 dump 设为 Complete/Kernel memory dump；符号路径指向构建产物 PDB。

| 用例 | 场景 | 期望 | 对应缺陷 |
|---|---|---|---|
| L4-1 | 基本拦截：受保护路径内删除 | `intercepts+1`，文件入暂存区，无栈溢出 | RB-01 |
| L4-2 | 内核栈占用：长路径（>1 KB）+ 深目录删除 | 不触发栈溢出；通知结构按变长分配 | RB-01 |
| L4-3 | 失败路径 fail-closed：暂存区不可写（权限/磁盘满模拟） | 拒绝删除返回 `STATUS_ACCESS_DENIED`，`DeleteDenied+1`，**数据未丢** | RB-04 |
| L4-4 | 递归删除大目录树（≥5000 文件） | 队列不击穿、无丢弃、无孤儿；耗时在基线内 | RB-08、RB-19 |
| L4-5 | `FileDispositionInformationEx` + `POSIX_SEMANTICS` 删非空目录 | 被拦截，不产生真删 | RB-22 |
| L4-6 | 队列打满（并发删除洪峰） | 预留式入队：文件未移动即拒绝，**孤儿数为 0** | RB-08、RB-20 |
| L4-7 | `RbfAllocNotify` 分配失败注入 | 预留槽位被释放，无泄漏 | RB-25 |
| L4-8 | 服务反复重启 / 崩溃（端口生命周期） | 无 use-after-free，无蓝屏 | RB-23、RB-24 |
| L4-9 | `sc stop rbminiflt`（卸载路径） | 不触发 0xA；等待 send thread 正确退出 | RB-28 |
| L4-10 | 服务端 stats 轮询持续运行（≥30 min） | 不触发 0x3B | RB-27 |
| L4-11 | 畸形 `REG_MULTI_SZ` 配置（无终止符 / 超 `DataLength`） | 不越界读，安全拒绝 | RB-26 |
| L4-12 | 驱动加载后立即删除（attach 窗口） | `protected_count>0` 且删除被拦截，无无保护窗口 | RB-29 |
| L4-13 | 卷卸载 / `\RBStore` 被删后删除 | rename 失败 → 缓存清除 → 自愈重建；fail-closed 保数据 | RB-19 |
| L4-14 | Verifier 全程 | 无 `DRIVER_VERIFIER_DETECTED_VIOLATION` | 全部 |

## 三、用户场景测试全景

> 本章从**真实用户视角**枚举场景，与第二章的分层视角互补：
> 第二章回答"测哪个层次"，本章回答"用户会遇到什么"。

### 3.1 维度 A：访问方式（用户从哪来）

| ID | 场景 | 期望 | 备注 |

| RB-30 | L1-9、L3-4、L5-5 | L1/L3/L5 | S-D10、S-D11、S-C5、S-H1 | 还原后无 `HIDDEN`/`SYSTEM`，UNC 可见 |

> 「用户场景」列指向第三章的场景 ID，形成 **缺陷 ↔ 技术用例 ↔ 用户场景** 的双向追溯：
> 修复某缺陷时，可反查它会触碰哪些用户场景；新增场景时，也可确认它守护的是哪些历史缺陷。

## 六、准入 / 准出标准

### 每次提交（Commit）

- L0 全绿：编译零警告、结构体断言通过、schema 派生 diff 为空
- L1/L2 全绿：`go test ./...` + 两套契约脚本
- 涉及还原/路径逻辑的改动：L3-2、L3-4 必须通过

### 每次构建（Build）

- 构建产物 SHA256 记录归档（供部署核对，防 RB-27/28 版本漂移）
- L3 全量通过

### 每次部署（Deploy）

冒烟清单（失败即回滚）：

1. 驱动 RUNNING 且 `fltmc` 已 attach 目标卷
2. `/health` 的 `driver.protected_count > 0`
3. [7/6] 探针冒烟：探针被暂存（LIVE）；否则按三态判定告警
4. 还原一次探针 → 属性无 `HIDDEN`/`SYSTEM` → UNC 可见
5. 部署后的 `.sys` SHA256 == 构建产物

### 版本发布（Release）

- L1~L3 **全自动全绿**
- L4：**Driver Verifier 全程无违规**，L4-1 ~ L4-14 全通过
- L5：L5-1 ~ L5-10 全通过，含大目录树逐字节比对与中文路径
- **用户场景（第三章）**：
  - P0 必过场景 **100% 通过**（S-A2/A3、S-B1/B3/B13、S-C1/C3/C9、S-D1/D7/D10、S-E1、S-G1/G10、S-H1~H3/H10）
  - P1 场景通过率 **100%**；P2 通过率 ≥ 95%（未通过项须有明确结论与缺陷单）
  - 8 个业务剧本（S-H1 ~ S-H10）全部执行，其中 ★ 标记的 4 个为阻塞项
- L6：压测达基线、故障注入无数据丢失、7×24 h 长稳无崩溃
- 无未修复的 P0/P1 缺陷（当前阻塞项：RB-02 驱动签名）
- 每次发布前完成 ≥1 小时探索式测试（重点：删除/还原组合顺序、多用户交叉操作）

## 八、风险与约束

| 风险 | 影响 | 应对 |
|---|---|---|
| 内核测试必然蓝屏 | 测试中断、环境损坏 | 独立测试机 + 每次快照 + dump 自动收集 |
